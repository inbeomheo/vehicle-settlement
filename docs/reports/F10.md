# F10 — R11 증빙 귀속 결함 수정

브랜치 `f9`, main 갱신 기준 `41621dc`. PG 54349 / 웹 3119. 지시 파일·R11 재현 테스트·AGENTS.md·DESIGN.md와 현재 인증/증빙 경로를 확인했고 작업 시작 시 `npm run db:migrate`를 실행했다.

## 원인과 수정

F9는 증빙 업로더의 **현재** users.driver_id 및 제출본을 기준으로 열람을 판단했다. 담당자 대리 업로드에는 기사 연결이 없고, 직접 업로더의 연결은 나중에 없어질 수 있으므로 과거 귀속의 근거로 사용할 수 없었다.

- 새 `0410_f10_evidence_owner.sql`과 Drizzle `evidence.owner_driver_id`(nullable drivers FK)를 추가했다. 증빙 메타 생성 시 서버가 부모 사용 건을 잠근 뒤 당시 기사 ID를 저장한다. 클라이언트 schema는 귀속 값 입력을 받지 않는다.
- DB trigger는 귀속 기사(null 포함)와 부모 사용 건 변경을 막는다. 사용 건 기사 변경이나 업로더 계정 변경, 기존 파일 콘텐츠 재전송으로 귀속을 바꾸지 않는다.
- 공통 `driverEvidenceFilter`/`assertDriverEvidenceAccess`가 현재 사용 건·현장 접근 검사에 더해 불변 귀속 일치를 검사한다. 목록, revision 내부, 다운로드, 콘텐츠 업로드, 삭제/교체, 메타 생성 멱등, HTTP 캐시 재생에 적용한다. 기존 캐시 응답에 owner 필드가 없어도 DB 귀속을 재검사한다.
- F9의 “다른 기사 제출본에 포함됐으면 영구 숨김” 수집 로직을 제거했다. A의 증빙이 B의 제출본에 남았다가 사용 건이 A로 돌아와도 귀속 A는 유지되며 다시 A에게 보인다. 다른 기사의 revision 자체는 기존대로 숨긴다.

## 기존 자료 복원 결정

현재 기사·현재 업로더·첫 발견 제출본만으로 귀속을 추정하지 않는다. 트랜잭션 시작 시각은 부모 행 잠금 획득보다 앞설 수 있으므로 시각만으로도 정렬하지 않는다.

사용 건 감사 before/after, revision snapshot, 현재 전체 증빙 목록의 **사용 건 version** 관측을 모은다. 각 증빙의 최초 등장 직전에 증빙이 없는 관측이 있고, 두 관측의 기사가 같으며 버전 차이가 1~2이고 구간 안에 상충하는 기사 관측이 없을 때만 복원한다. 증빙 생성에는 최소 한 번, 기사 변경 후 원상 복귀에는 두 번의 별도 version 증가가 필요하므로 이 짧은 구간은 생성 당시 귀속을 증명한다. 넓은 공백·이력 누락·충돌은 더 많이 복원하려고 추측하지 않고 null(담당자 전용)로 남긴다. 감사 원문·제출본 원문은 변경하지 않는다.

이 보수적 정책은 일부 정상 과거 증빙도 담당자 전용으로 남길 수 있다. 파일과 정산 근거는 그대로 보존되며 현재 기사로 일괄 이관하지 않는다. DB의 불변 제약 때문에 null 역시 이후 임의 변경할 수 없다.

## 제출·정산과 화면 결정

지시의 권장안을 따라 **이전 기사/귀속 불명 증빙도 사용 건의 근거로 인정하고 노출만 제한**한다. 기존 업로드 상태·삭제/교체 여부·현장 정책 검사를 유지한다. 기사 제출, 담당자 승인, 명세 확정 모두 기존 유효 증빙 전체를 검사한다.

증빙을 숨기면 기사 폼의 사전 검사가 추가 촬영을 강제할 수 있어 `restricted_evidence_count`, `restricted_evidence_satisfies_policy`를 추가했다. 파일명·ID·본문 없이 현재 제한 건수와 정책 충족 여부만 제공한다. 같은 현장의 서버 상세에 근거한 경우에만 클라이언트 사전 검사에서 사용하며 최종 판단은 서버가 계속 수행한다. 편집 화면과 읽기 전용 화면에 “증빙 N건은 담당자만 볼 수 있습니다. 사용 건의 제출·정산 근거로 보관됩니다.”를 표시한다.

React 점검 스킬을 적용해 안내를 작은 공용 컴포넌트로 만들고 기존 client 경계·폼 이벤트·로딩 흐름을 유지했다. 새 effect/전역 상태/외부 의존성을 추가하지 않았다.

## 검증

수정 전 `F10-evidence-owner.test.ts`의 첫 회귀 5개가 모두 실패했다. 담당자 대리 업로드 후 최초 제출 전 기사 변경, 직접 업로더의 역할/기사 연결 해제, 이전 파일 변경·메타 재생, HTTP 캐시 재생, 숨김을 전제로 한 필수 증빙 정책을 재현했다.

최종 테스트는 다음을 포함한다.

- 리뷰의 두 노출 경로와 인증된 파일 GET 404, 담당자의 원본 바이트 조회 유지.
- 이전 증빙 교체·삭제·client_upload_id 재생 차단, 새 기사 본인 업로드 조회·다운로드.
- owner 필드가 없는 구버전 HTTP 캐시 응답의 역할 변경 후 재생 차단.
- 기사 왕복 변경 시 원래 귀속 보존 및 원래 기사 조회 회복, DB 귀속 변경 거부.
- null 귀속 기사 접근 차단, 제한된 유효 증빙만으로 제출·승인·명세 확정 성공.
- 실제 PostgreSQL에서 구버전 컬럼 상태로 되돌린 뒤 새 마이그레이션 실행: 감사/제출본 복원, 기사 변경 후 신규 귀속 복원, 누락·충돌·넓은 공백 null 처리, 감사·revision 원문 보존.
- 모바일 E2E: 제한 안내, 파일명 비노출·GET 404, 새 사진 없이 제출, 승인 후 읽기 전용 안내.

첫 전체 E2E는 F10을 포함해 111개 통과, 기존 F8B autosave 한 건이 `page.evaluate: Execution context was destroyed`로 실패했다. trace에 실패 직전 Next Fast Refresh rebuilding이 기록되었으며 IndexedDB 조회가 탐색으로 중단되었다. 코드/파일 변경과 병행 테스트를 중단한 상태로 필수 명령 전체를 다시 실행했고 통과했다. 테스트 기대값을 완화하거나 제품 동작을 바꾸지 않았다.

최종 검증:

- `npm run db:migrate`: 작업 시작 시 실행 및 새 F10 마이그레이션 적용 모두 통과.
- `npm run typecheck && npm run lint`: 통과.
- `npm test`: **58개 파일, 345개 테스트 통과**(F10 8개 포함, 실제 PostgreSQL).
- `npm run build`: 프로덕션 빌드 통과.
- `npm run format` 실행, `npm run format:check`: 통과.
- `npm run test:e2e`: **112개 모두 통과**(5.1분). 앞서 중단됐던 F8B autosave와 F10 모바일 시나리오 모두 통과. 개발 DB 6개 업무 테이블 실행 전후 건수 동일.

코드 커밋은 `3b82c7d`(불변 귀속·이력 복원·서비스 회귀), `6fa795c`(기사 안내·제출 사전 검사·모바일 E2E)로 분리했다. 운영·설계·API 문서와 이 보고서는 별도 문서 커밋으로 정리한다. 빌드/E2E 산출물은 ignore 대상으로 유지하고 최종 작업 트리를 clean 상태로 마무리한다.

## 공용 파일과 범위

공용 변경은 `src/server/authz.ts`, `src/server/db/schema.ts`, migration journal, 사용 상세 반환형에 한정했다. `http.ts`는 기존 재생 접근 검사에서 새 필터를 재사용하므로 수정하지 않았다. UI는 증빙 안내·사전 검사만 변경했다. 금액·상태 모델, 기존 마이그레이션, 패키지 의존성은 변경하지 않았다. `.env`, `.data`, storage, 빌드 산출물은 커밋하지 않는다.
