# H-FIX — 4차 검토 결함 및 E2E 회귀

## 범위와 환경

- 워크트리의 PostgreSQL `54404`, 웹·Playwright `3204`만 사용했다.
- 통합 테스트는 실제 PostgreSQL의 파일별 격리 DB, E2E는 전용 `vehicle_e2e`를 사용했다. 개발 DB의 업무 테이블 건수는 실행 전후 동일함을 global setup에서 확인한다.
- 운영 DB·배포 비밀 파일·다른 포트는 사용하지 않았다. 패키지 추가와 마이그레이션은 없다.

## 결함별 원인·수정·회귀

### 1. 운행 결재의 보류액 합산

`approvals.ts`의 요약 집계가 반려만 제외하여 HELD까지 포함했다. 행의 PENDING/APPROVED 규칙과 요약 집계를 맞추고 `held_amount`, `held_count`, `held_unknown_count`를 별도로 반환한다. 화면 상단에 보류 공급가·미정 개수를 구분하며 Excel에도 보류 열과 별도 합계를 추가했다. 취소·삭제·고객청구 제외 및 공급가 환산 규칙은 유지한다.

- `tests/integration/H-FIX-money.test.ts`: 승인 300,000원 + 보류 50,000원의 행·상단·Excel 합계 일치, 보류 미정의 별도 집계.
- `tests/e2e/H-FIX.spec.ts`: 결재 상단에 승인 대상 합계와 보류액이 분리되어 보임.
- 수정 전 요약/Excel 합계 350,000원으로 실패했고 수정 후 승인 대상 300,000원, 보류 50,000원으로 통과했다.

### 2. 기본운임 반려 후 승인 통행료가 미확정으로 표시됨

`ledger.ts`가 합산할 기본운임이 없을 때 HELD만 0으로 처리하고 REJECTED는 null로 남겼다. PENDING/APPROVED 기본운임이 없으면 0, 실제 대상 줄의 금액이 없으면 null로 구분한다. 공용 `quickApprovable`과 승인 트랜잭션이 동일한 대장 금액을 사용한다.

- 통합 회귀: 기본운임 반려 + 통행료 개별 승인 시 기본 0원·추가/총 50,000원, 바로 승인 성공. 실제 미정 기본운임은 여전히 null.
- 화면 회귀: 해당 건이 선택 승인에 포함되고 승인 1건으로 완료됨.
- 기존 F2-MONEY2의 보류·청구 확인·버전/금액 재검사도 유지한다.

### 3. 소속 변경 시 공유 사업자 원장 오염

`allowExistingBusiness`가 기존 사업자 연결 허용과 원장 수정 허용을 함께 담당했다. 관리자가 다른 기존 사업자로 옮길 때 폼에 남은 상세를 원장에 쓰고 있었다.

- 관리자 기사 정보 저장은 기존 사업자로 이동하거나 CARRIER/공유 사업자를 유지할 때 원장의 상호·대표자·주소·업태·종목을 그대로 사용한다. 오래 열린 폼의 이전 값이 와도 원장에 쓰지 않는다.
- 동일 사업자번호의 현재 본인 전용 DRIVER_BUSINESS만 상호·상세 수정이 가능하다. 다른 기사의 과거·미래·비활성 소속도 공유 판정에 포함한다.
- 기사 본인의 공유 원장 변경 요청은 기존처럼 거부한다. 관리자의 명시적 원장 수정은 기준정보 > 거래처를 사용한다.
- 관리자 폼은 기존 번호와 일치하면 원장 값을 채우고 읽기 전용으로 표시한다. 현재 소속 우선, 나머지는 서버와 같은 생성일·ID 순으로 중복 번호를 해석한다. 조회 전/실패 시 저장을 막고 재시도를 제공한다.
- `H-FIX-business.test.ts`: 기존 DRIVER_BUSINESS/CARRIER로 이동, 현재 공유 소속 유지(과거·미래·비활성), 본인 전용 수정 허용을 실제 DB로 검증한다. G-BIZ/JOIN의 관리자 공유 원장 직접 수정 기대를 새 결정에 맞춰 갱신했다.
- E2E는 이전 대표자에서 원장 대표자로 자동 채움, 상호 포함 다섯 칸 읽기 전용, 저장 뒤 원장 정보 보존을 검증한다. 수정 전에는 이전 대표자가 남아 실패했다.

### 4. 사업자번호 없는 기존 운송사 연락처 수정 불가

가입용과 수정용 스키마가 같은 필수 사업자번호 규칙을 썼고 HTML required도 고정이었다. PATCH에서만 빈 번호를 받을 수 있게 하고, 서버가 현재 소속의 빈 번호·동일 상호인 경우에만 소속을 유지한다. 새 사업자 생성·일반 신규 가입은 계속 번호가 필수다. 폼도 같은 기존 소속 유지에 한해서 required를 해제한다.

- 통합 회귀: 관리자/본인 연락처 수정, 소속 행 유지, 빈 번호 신규 생성 차단.
- E2E: 번호 없는 CARRIER를 지정한 실제 가입 링크로 가입한 뒤 관리자/본인 화면에서 연락처 PATCH·저장 결과 확인. 수정 전에는 브라우저 검증으로 요청이 전송되지 않아 실패했다.

### 5. 기준정보 관리 열 잘림

거래처의 모든 상세 필드를 개별 열로 출력하고 각 셀에 최소 너비를 두어 표가 화면보다 넓었다. 점검 결과 회사 정보와 계약·단가에도 같은 문제가 있었다.

- 거래처는 구분/번호, 담당자/연락처/계좌를 묶고 사업자 상세는 펼치기와 수정 폼에서 제공한다.
- 회사 정보와 계약·단가도 주요 열을 묶고 나머지 정보를 펼쳐 볼 수 있게 했다. 고정 표 너비·줄바꿈·관리 열 너비로 버튼을 보존한다. 작은 화면의 표는 기존처럼 내부 가로 스크롤을 사용할 수 있다.
- 새 E2E가 1280·1440px에서 거래처·기사·차량·현장·소속·회사·단가·공종의 표 너비, 수정 버튼 경계, 문서 가로 넘침을 검사한다. 두 해상도 모두 수정 전 거래처/회사/단가에서 실패, 수정 후 통과했다.

### 6. 기존 E2E 회귀 정리

- F4-DETAIL: G-DELETE가 추가한 삭제 버튼을 포함해 관리 버튼 6개를 확인한다. 버튼 수 외에 모든 버튼의 화면 내 경계도 계속 검사한다.
- F8a-manager: 실제 실패 스냅샷에서 대상인 비활성 `담당자 나` 카드가 없었다. G-DELETE의 의도된 기본 숨김에 맞춰 ‘꺼진 계정 1명 보기’ 체크박스를 켠다. 다른 사용자 선택 시 입력/저장 대상 일치, 같은 프레임의 2회 제출이 1요청만 전송되고 다른 선택이 잠기는 검증을 유지한다. 사용자 관리 앱 코드는 변경하지 않았다.
- W8b-admin: 단가 표의 묶인 열에서 최소요금 미설정 표시가 `최소요금 (원): 없음`으로 바뀌어 이전 단독 `없음` 셀 선택자가 실패했다. 새 문구가 표시되는지 검증하도록 갱신했다.
- F2-lookup: POST `/api/uses` 응답만 기다린 뒤 `page.goto('/m/import')`를 실행하고 있었다. 운행 폼은 응답 이후 `syncQueue`/`getDraft`를 마치고 `location.assign('/m/uses/:id')`를 수행하므로 두 이동이 경합할 수 있다. 저장 결과 ID의 상세 URL 도착을 기다린 뒤 가져오기로 이동한다. 임의 지연·오류 재시도·서비스워커 변경 없이 실제 저장 완료 흐름에 동기화했다.

## 공용 파일 변경

- `src/components/driver-information-fields.tsx`: 가입·기사 수정 공용 필드의 선택적 번호 required 및 읽기 전용 상호. 가입 기본 필수는 유지한다.
- `src/components/driver-profile-editor.tsx`: 관리자/기사 공용 수정 폼의 기존 사업자 자동 채움 및 상세 보호 표시.
- `src/components/manager/master.tsx`: 기준정보 공용 표의 열 묶기·상세 펼치기·너비.
- `src/components/manager/approvals.tsx`, `src/server/services/approvals-export.ts`: 보류 분리 표시·출력.
- `docs/API.md`: 변경한 합계 응답·사업자 수정 계약 문서화.
- 관련 기존 테스트 G-BIZ/JOIN/LIST/F2/F4/F8a/W8b를 새 계약 및 의도된 G-DELETE 화면에 맞춰 갱신했다.
- DB 스키마·패키지·권한 공용 헬퍼·레이아웃·오프라인 셸 구성은 변경하지 않았다. 오프라인 대상 파일에 Next 전용 import를 추가하지 않았다.

## 검증 결과

- 결함별 실패 회귀를 먼저 저장소에 추가·실행했다. 최초 새 통합 11건 중 9건 실패, 새 E2E 6건 모두 실패를 확인했다. 이후 미정 금액 구분 통합 1건을 추가했다.
- `npm run typecheck`, `npm run lint`, `npm run format:check`: 통과.
- `PG_PORT=54404 APP_URL=http://localhost:3204 npm test`: 95파일, 596건 통과.
- 첫 전체 E2E: 205건 통과, 단가 표의 이전 문구 선택자 1건과 G-PERIOD의 로그아웃 요청 `socket hang up` 1건 실패. 선택자는 현재 문구에 맞춰 수정했다. 소켓 오류는 HTTP 서버 오류 응답 전 연결 종료였으며, 관련 13건 재실행과 최종 전체 재실행에서 재현되지 않았다. 이에 로그아웃 앱 코드는 변경하지 않았다.
- `PG_PORT=54404 PORT=3204 APP_URL=http://localhost:3204 npx playwright test tests/e2e/H-FIX.spec.ts tests/e2e/W8b-admin.spec.ts tests/e2e/G-PERIOD.spec.ts`: 13건 통과(57.3초).
- `PG_PORT=54404 PORT=3204 APP_URL=http://localhost:3204 npx playwright test`: 최종 207건 모두 통과(14.7분), 실패·재시도 없음.
- 최종 E2E의 개발 DB 업무 테이블 건수는 실행 전후 모두 0으로 동일했다. 관련 기존 E2E, 새 회귀 6건, 전체 오프라인·보안·정산 시나리오를 포함한다.
- 1280·1440px 거래처 화면 PNG를 직접 확인하여 열·관리 버튼이 화면 안에 표시되는 것을 점검했다.

## 남은 문제

요청 범위에서 재현되는 잔여 결함은 없다. 첫 전체 실행의 일회성 로그아웃 연결 종료는 위와 같이 기록했으며 후속 두 실행에서 재현되지 않았다. 운영 배포는 수행하지 않았다.
