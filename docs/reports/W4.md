# W4 — 월 정산·출력·지급/입금·조정·기사 내 정산

작업일: 2026-09-29. 브랜치: `feat/w4`. 전용 PostgreSQL: `54333`, 개발 포트: `3104`.

## 구현 내용

- PAYABLE/RECEIVABLE 독립 명세의 후보 조회, 초안 생성·편집, 포함·보류 사유, 예정일, 확정, 취소·재작성 연결을 구현했다. 종료일 이전의 미정산 과거 사용 건을 후보에 포함하고 `전월분`을 표시한다.
- 확정은 명세 잠금 → 부모 사용 건 ID 순 잠금 → 비용 ID 순 `FOR UPDATE` → 승인·단가·승인액·세액·증빙·방향·거래처·삭제·기간 재검사 → 조건부 비용 잠금 UPDATE → `is_active_lock` 부분 유니크 검사 순서다. 실패는 전부 롤백하고 `422 CONFIRM_BLOCKED`와 항목별 사유를 반환한다.
- 확정 시 문서번호, 거래처·회사·담당자·발행일, 사용 당시 항목과 공급가·세액·총액을 고정한다. HELD 항목은 이력으로 보존하되 합계·잠금에서 제외한다. 명세 합계는 라인별 금액을 그대로 합산한다.
- 확정 명세의 전액 지급/입금 기록, 방향별 PAYMENT/RECEIPT 검증, 멱등 재전송, 오입력 취소 이력, 미지급/입금 복귀를 구현했다. 유효 지급·입금 기록이 있으면 명세 취소를 거부한다.
- 지급 관리에 확정 명세 목록, 미지급·완료·예정일 경과 필터, 거래처/현장별 미지급 건수·금액과 경과 금액을 제공한다. 여러 현장이 포함된 명세의 현장별 금액은 해당 항목만 합산한다.
- 지급 완료 원명세에 연결된 ADJUSTMENT 라인을 생성한다. 음수 공급가와 필수 사유를 지원하고 세액은 서버에서 계산한다. 원명세는 변경하지 않으며 다음 정산 후보로 반영한다.
- ExcelJS 엑셀과 PDFKit 한글 PDF를 동일한 출력 모델로 생성한다. 문서번호·종류·거래처/회사·기간·발행일·확정시각·담당자·예정일, 모든 요청된 항목 열, 합계, 확인란, 세금계산서 아님 문구를 포함한다. 확정/취소 출력은 저장된 스냅샷만 사용한다. 초안은 PDF 워터마크 및 엑셀 초안 표기/인쇄 머리말을 사용한다.
- Noto Sans KR 정적 400 굵기 TTF와 OFL 전문을 번들했다. Google Fonts의 가변 원본에서 정적 인스턴스를 만든 과정과 원본 SHA-256은 `docs/THIRD_PARTY.md`에 기록했다. 앱 실행에 추가 npm 패키지는 필요하지 않다.
- `/m/statements`, `/m/statements/[id]`, `/m/payments`, `/d/settlements`를 한국어·반응형 화면으로 구현했다. 로딩/빈 상태/오류, 입력 검증, 포함/보류 선택, 차단 사유, 취소·재작성·조정, 다운로드, 지급/입금 이력을 연결했다.
- 기사 전용 조회는 본인 기사와 유효 배정 현장만 선택하고, 본인 PAYABLE 확정 항목의 금액만 합산한다. 다른 기사 금액, 전체 명세 총액, 고객 청구, 지급 기록의 전체 금액을 반환하지 않는다. 전체 명세 상세/엑셀/PDF URL은 기사에게 404다.
- 모든 업무 변경은 W1 트랜잭션·권한·감사로그·HTTP 멱등 래퍼를 사용한다.

## API 및 서비스 연결

요청/응답은 W1과 같은 snake_case 본문, `{ data }` 성공, `{ error }` 오류다. 후보 조회 파라미터는 요청 명세에 맞춰 camelCase다.

- 추가 조회: `GET /api/statements`, `GET /api/statements/:id`, `GET /api/statements/mine?periodStart&periodEnd`.
- 후보: `GET /api/statements/candidates?direction&counterpartyId&periodStart&periodEnd&statementId?`.
- 초안 생성 본문: `client_request_id`, `direction`, `counterparty_id`, `period_start`, `period_end`, `due_date?`, `replaces_statement_id?`, `items: [{ charge_line_id, inclusion?, hold_reason? }]`.
- 항목 편집: `PATCH /api/statements/:id/items`에 `version`, `items?`(배열 전체 교체), `due_date?`. 확정은 `{ version }`, 취소는 `{ version, reason }`.
- 지급/입금: `POST /api/statements/:id/payments`에 `client_request_id`, `kind`, `amount`, `paid_on`, `method`, `reference?`, `memo?`. void는 `{ reason }`.
- 지급 조회: `GET /api/payments/overview`에 `direction`, `state=ALL|UNPAID|OVERDUE|PAID`, 거래처/기간 필터와 페이지·정렬을 지원한다.
- 조정: `POST /api/adjustments`에 `adjusts_statement_id`, 원명세의 `charge_line_id`, `supply_amount`, `reason`, `effective_date?`.
- 목록은 `page`, `pageSize`, `total`, `totals.pageSum`, `totals.filteredSum`을 구분한다.
- 서비스 함수/입력 검증은 `src/server/services/statements*.ts`, `payments.ts`, `adjustments.ts`, 출력 모델·렌더러는 `src/server/export/*`, 다운로드 응답은 `services/exports.ts`에 있다.

## 설계의 모호한 부분에 대한 결정

- 다른 초안에 INCLUDED로 있는 라인은 후보에서 제외 사유를 표시한다. 초안 자체는 비용을 독점하지 않으므로 API로 작성된 중복 초안은 허용하고, 최종 확정 경쟁에서 하나만 성공한다.
- 접근 권한이 일부 현장에만 있는 담당자는 명세의 모든 현장에 접근할 수 있어야 전체 명세를 조회/변경/출력할 수 있다. 혼합 명세의 일부 권한만 있으면 전체 단건은 404, 목록에서도 제외한다.
- 기사는 `/api/statements/mine`으로 본인 부분만 조회한다. 정산 담당자용 전체 문서는 본인 항목이 포함돼 있어도 다운로드할 수 없다.
- 조정의 원래 사용일은 유지한다. `rate_basis_date`를 반영 기준일로 사용하여 원명세의 정산 종료일 다음 날 이후에만 후보로 노출한다. 기본 반영일은 서울 오늘과 원기간 다음 날 중 늦은 날이다.
- 530,000원 수용 사례는 공급가와 총액이 같도록 면세 테스트 데이터로 구성했다. W1이 일반 추가비에 기본 적용하는 VAT_EXCLUDED는 변경하지 않았다. 과세 사례는 각 5원 공급가 두 줄의 세액 1원씩을 합산해 총액 12원이 됨을 별도로 검증했다.
- `W4_RENDER_QA=1`로 출력 테스트를 실행하면 Git 제외된 `.data/w4-qa/`에 육안 확인용 PDF/엑셀을 생성한다. 이는 앱 런타임이나 일반 테스트의 필수 의존성이 아니다.

## 검증 결과

최종 코드에서 다음 명령이 모두 통과했다.

```sh
npm run typecheck
npm run lint
npm test
npm run build
npm run format:check
npm run test:e2e -- tests/e2e/W4-settlement.spec.ts
```

- Vitest: **10개 파일, 64개 테스트 통과**. 이 중 W4는 실제 PostgreSQL 통합 **24개 테스트 / 4개 파일**이다.
- 검증 범위: U001 5톤 회당 200,000 + 대기비 30,000 / U002 1톤 일대 300,000·5운행 = 530,000, 늦은 승인 9/30 사용분의 10월 400,000 전월분 이월, 두 담당자·별도 PG 커넥션 동시 확정, 방향 독립, 미확정/0원 구분, 보류 잠금 제외, 증빙 재검사, 최종 유니크 방어와 전체 롤백, 버전 충돌, 지급·입금 멱등/void/취소 거부, 음수 조정, 스냅샷 고정, 엑셀 재독입, 기사/담당자 권한과 권한 회수 후 멱등 재생 차단.
- Playwright: **2개 통과**. 데스크톱 정산 담당자 로그인 → 새 정산 → 확정 → PDF/엑셀 HTTP 200 및 실제 다운로드 → 지급 완료. 360px 기사 내 정산과 다른 기사 명세 export 404.
- ego-browser: 월 정산 폼의 데스크톱 및 360px 배치 육안 확인, 모바일 페이지 가로 넘침 없음 확인.
- PDF: Poppler로 확정 한 페이지·긴 비고/여러 페이지 초안을 렌더링해 한글, 표, 워터마크, 합계, 페이지 번호를 확인했다. 텍스트 추출에서 문서번호와 `총액 300,000원`을 확인했다. 꼬리말이 불필요한 빈 페이지를 만들던 문제를 수정했다.

## 공용 파일 변경

- **`src/server/http.ts`만 공용 변경**: `authorizeReplay`에 8줄 추가. 저장 응답의 `statement_id`, 또는 `statement_no`와 `id`를 발견하면 W4 `rawStatement`로 현재 역할·현장 접근 권한을 다시 검사한다. 지급 응답에는 사용 건 필드가 없어 기존 W1 재생 검사만으로는 배정 회수를 반영하지 못하므로 필요했다.
- DB 스키마·마이그레이션·package.json/lock·authz·레이아웃/내비게이션 변경 없음.
- 요청에 따라 작업 보고서인 이 파일을 추가했다. `.env`는 54333/3104로 로컬 설정했으며 커밋하지 않는다. `.data/`, `storage/`, 출력 QA 파일과 테스트 산출물도 커밋하지 않는다.

## 남은 문제

알려진 수용 기준 미충족이나 테스트 실패는 없다. 부분 지급·선지급·상계는 DESIGN의 v1 제외 범위를 유지한다. 코디네이터가 `feat/w4`의 커밋을 병합하면 된다.
