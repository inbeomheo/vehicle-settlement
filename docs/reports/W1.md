# W1 — 기반 + 사용 건 도메인 코어 완료 보고

작업일: 2026-09-29. 브랜치: `main`.

## 구현 내용

- Next.js 15 / React 19 / TS strict / Tailwind 4 / ESLint / Vitest / Playwright 설정. Node 24, npm 스크립트와 환경 예제.
- embedded-postgres를 `.data/pg`, 포트 54329에서 실행·재사용. Drizzle **23개 전체 테이블**, FK·기간 제약·부분 유니크 인덱스·전역 문서번호 시퀀스. 참조된 계약의 가격/단위/시작일/계산근거 변경 방지 트리거와 안전한 적용 종료일 닫기.
- DB 세션 로그인·로그아웃·me, bcrypt 비밀번호, 1회/7일 초대·수락·취소, 즉시 비활성/현장 배정 회수 반영. 로그인·초대 페이지와 역할별 `/d`, `/m` 셸·메뉴·플레이스홀더.
- 공용 HTTP 래퍼: 인증·zod·한국어 오류·request_id·트랜잭션 멱등 응답 재생. 감사로그와 접근 범위/기사 개인정보·고객 청구 제거.
- 사용 건 생성/조회/중첩 수정, version 충돌, client_request_id 중복 방지, snapshot·소속 지급처·PROXY 기록. 8종 과금 단위, 단가 조회·BASE 자동 구성, 순수 Decimal 금액·세금 함수, 추가비 요청/검수.
- 제출 revision, 승인·라인별 승인/보류/거절·승인액, 보완·재제출, 변경 시 승인 해제·이전 기록 보존, 명세 잠금 거부, 기사 확인·복사·논리 취소.
- 증빙 메타·바이너리 업로드·다운로드·교체 이력·논리삭제. SHA-256, 20MB 제한, 실제 파일 시그니처/MIME 검증, PENDING/UPLOADED/FAILED, 파일만 재시도, 현장별 필수/대체증빙 검사.
- 데모 계정 5개, 현장 2개, 차량 3대, 기사 2명, 운송사 2곳·기사사업자·고객, 계약 3개. 계정과 실행 방법은 루트 README.

## 테스트 헬퍼 사용법

`tests/helpers/database.ts`:

- `testDatabase()` → `() => { db, pool, name, cleanup }`. Vitest beforeAll/afterAll에 독립 DB 생성·마이그레이션·삭제를 등록한다. 테스트 파일끼리 병렬 안전하다. 한 파일의 test.concurrent에는 DB를 공유하지 말고 `createTestDatabase()`를 각각 호출한다.
- `createTestDatabase()` → 위 객체의 Promise. 필요하면 테스트/스위트 단위로 직접 수명 관리한다. 테스트 계정에 CREATE DATABASE 권한이 필요하다.

`tests/helpers/factories.ts`:

- `factories(db)` → `company`, `project`, `counterparty`, `vehicle`, `driver`, `workType`, `user`, `assignment`, `affiliation`, `rate`, `session`, `context`.
- 모델 생성 함수의 마지막 인자로 Drizzle insert의 부분 override를 받는다. `user` 기본 비밀번호는 `password1234`.
- `setupScenario(db, { evidence_policy? })` → 연결된 현장·기사·차량·지급처·계약·관리자·기사 사용자·배정, `adminCtx`, `driverCtx`, 생성용 `input`.

```ts
import { testDatabase } from '../helpers/database';
import { setupScenario } from '../helpers/factories';
import { createUse } from '../../src/server/services/uses';

const database = testDatabase();
// it(...) 안에서:
const s = await setupScenario(database().db);
const use = await createUse(s.driverCtx, {
  ...s.input,
  client_request_id: crypto.randomUUID(),
  trips: [{ seq: 1, origin: '상차장', destination: '현장' }],
});
```

`tests/helpers/routes.ts`의 `callRoute(db, handler, { method?, path?, token?, body?, rawBody?, headers?, params? })`는 실제 Request와 Promise params를 만들어 Route Handler를 직접 호출한다. `withDatabase`의 AsyncLocalStorage로 테스트 DB를 주입하므로 전역 환경변수 DATABASE_URL을 바꾸지 않는다.

```ts
import { POST } from '../../src/app/api/uses/route';
import { callRoute } from '../helpers/routes';

const { token } = await s.f.session(s.driverUser.id);
const response = await callRoute(database().db, POST, {
  method: 'POST', path: '/api/uses', token,
  headers: { 'idempotency-key': crypto.randomUUID() },
  body: s.input,
});
```

## 서비스 모듈·주요 함수

공통 타입: `src/server/context.ts`의 `Context = { db, user, request_id, session_id? }`. `db`는 일반 Drizzle DB 또는 트랜잭션이다. public 서비스는 입력을 재검증하고, 변경은 트랜잭션 안에서 현재 사용자·권한·버전·명세 잠금을 검사하고 감사로그를 기록한다. 세부 입력 타입은 `src/server/services/schemas.ts`, JSON 계약은 `docs/API.md`에 있다.

| 모듈 | 주요 함수 시그니처 |
|---|---|
| `services/uses.ts` | `createUse(ctx, input: CreateUseInput)`, `updateUse(ctx, id, input: UpdateUseInput)`, `getUse(ctx, id)`, `listUses(ctx, query)` |
| 동일 | `submitUse(ctx, id, {version})`, `approveUse(ctx, id, {version, lines?, comment?})`, `requestFix(ctx, id, {version, fix_items, comment?})` |
| 동일 | `reviewChargeLine(ctx, lineId, {version, line_review_status, approved_amount?, reason?})`, `confirmByDriver(ctx, id, {version})`, `copyUse(ctx, id, {client_request_id, use_date?})`, `cancelUse(ctx, id, {version, reason})` |
| 동일, W4 공용 | `rawUse(ctx, id, lock?)`, `rawDetail(ctx, use)`, `assertEvidenceSatisfied(ctx, use)`, `assertUnlocked(ctx, useId)`, `assertVersion(use, version)`, `atomic(ctx, fn)` |
| `services/evidence.ts` | `createEvidence(ctx, useId, input)`, `uploadEvidence(ctx, id, bytes: Buffer, mime)`, `downloadEvidence(ctx, id)`, `replaceEvidence(ctx, id, input, reason)`, `deleteEvidence(ctx, id, reason)` |
| `services/rates.ts` | `lookupRate(ctx, query)`, 내부 조회용 `findRate(db, query)`, `suggestedQuantity(unit, completedTrips)` |

| `db/client.ts` | `getDb()`, `createDatabase(url)`, `withDatabase(db, fn)` |

`withRoute` handler는 `{ ctx, db, input, params, request, request_id }`를 받는다. `auth:false`이면 ctx=null. 실제 Next Route Handler의 두 번째 인자는 `{ params: Promise<Record<string,string>> }`이다. 파일 PUT은 원시 body이므로 `source:'none'`이며 자체 해시 멱등성을 쓴다.

W4에서 `rawDetail`은 전체 청구를 포함하는 **서버 내부용**이다. 기사에게 내보낼 때는 `getUse` 또는 `redactForDriver`를 사용한다. 잠금 순서는 부모 사용 건 → 비용(id 순)이고, 비용만 잠그는 확정은 잠금 획득 후 사용 승인 상태와 증빙을 재검사해야 한다. 기간 종료와 번호 채번·부분 유니크는 현재 마이그레이션에 있으므로 복제하지 않는다.

## DESIGN과 달라지거나 구체화한 점

기존 테이블·필드·enum·오류코드의 삭제/이름 변경은 없다. DESIGN 수정은 다음 세 가지뿐이다.

1. 한글로만 적혀 있던 회사 설정 필드를 `name`, `biz_no`, `address`, `representative`, `default_tax_mode`, `settlement_contact`로 명시했다.
2. 예상하지 못한 서버 오류를 내부 상세 없이 표현하는 `INTERNAL_ERROR`(500)를 추가했다. 기존 업무 오류 형식과 코드는 유지했다.
3. 세부 API 계약/보고서 링크를 추가했다.

설계가 생략한 선택은 `docs/API.md`와 `docs/ASSUMPTIONS.md`에 기록했다: 전역 시퀀스(월별 초기화 없음), 단가 구체성의 우선순위·동률, 배열 전체 교체, 라인 검수의 부모 version, 공급가 기준 승인 override, 실패 응답 미저장, 바이너리 업로드의 고유 해시 멱등성, SUBMITTED 내용 변경도 새 revision으로 분리하는 규칙. 금액은 서버가 계산하고, 기존 승인과 제출 snapshot은 보존한다.

## 공용 파일 및 후속 범위

W1이 소유한 초기 저장소 전체에 스키마·package.json·http.ts·authz.ts·공용 레이아웃·내비게이션을 생성했다. 후속 스키마 변경은 **새 마이그레이션**으로 추가한다. 새 UI 메뉴 본체는 기존 플레이스홀더 파일에 구현하면 된다.

확인된 W1 수용 기준 미충족 사항은 없다. 후속 작업은 예정된 기사/담당자 화면 본체·기준정보 API·정산/지급 서비스·엑셀/PDF/PWA·import·브라우저 E2E다. W4용 테이블과 잠금/계산/증빙 검사 헬퍼는 준비됐으며 W1이 해당 업무 API를 대신 구현하지 않았다. 출력 라이브러리·폰트와 오프라인 자산은 해당 워커가 추가한다.

Git은 기반/서버 코어/인증 셸·시드/테스트·인계 문서 단위로 main에 커밋한다. 로컬 DB·파일 저장소·비밀값은 추적하지 않는다.
