# G-BIZ 거래처 사업자 정보와 명세 출력

## 원인과 수정

- 거래처에는 대표자·주소·업태·종목, 회사에는 업태·종목이 없어서 거래명세표 머리를 채울 수 없었다. `0760_business_details.sql`에 nullable text 6개와 길이 CHECK를 추가했다. 대표자 200자, 주소 500자, 업태·종목 100자이며 빈 문자열은 null이다. 기존 회사 대표자·주소와 기존 자료는 유지한다. journal의 마지막 when보다 큰 값을 추가하고 DEPLOY 개수(17)와 이전 스키마 재현 테스트를 갱신했다.
- 관리자 거래처·회사 정보, 신규 사업자 `/join`·`/invite`, 가입 링크/개별 초대의 새 사업자 등록, 기사 본인 정보와 관리자 기사 정보 수정의 공통 폼을 연결했다. 새 사업자 폼의 업태·종목만 운수·화물을 기본으로 채우며 모두 선택 입력이다. 지정된 기존 사업자로 가입할 때는 필드를 숨기고 전송하지 않는다. 서버도 지정 소속의 사업자 값 전송을 거부한다.
- 기사의 새 상세 필드 변경은 현재 소속이 본인 전용 DRIVER_BUSINESS일 때만 허용한다. CARRIER 또는 다른 기사 소속 이력이 있는 사업자는 읽기 전용이다. 동일값 재전송과 필드 생략은 허용하고 관리자 기사 정보 수정은 허용한다. 공통 관리 잠금·사용자 version·감사·실패 시 전체 롤백·기존 차량 보안 규칙을 유지했다.
- 거래명세표는 현재 거래처/회사 값을 출력한다. 월 정산 PDF/XLSX는 사업자 상세를 명세 머리 스냅샷에 담아 출력하며, 확정 후 기준정보를 바꿔도 고정된 값만 사용한다. PAYABLE은 거래처가 공급자, 회사가 공급받는자이며 RECEIVABLE은 반대다. 미등록 값은 빈칸/생략하고 담당자 이름을 대표자로 대체하지 않는다. 긴 머리글은 XLSX 행 높이와 PDF 줄바꿈·페이지 나눔으로 처리했다.
- 선택 목록은 기존 최소 필드 조회를 유지했다. 대표자·주소는 현장 담당자 기사 목록과 거래명세표에서 제외하고 공통 중첩 응답·감사·멱등 재생에서도 제거한다. 기사 본인 정보 전용 GET은 본인 소속 정보를 보여 준다.
- 설명서 관리자 거래처/회사 정보와 정산 담당자 거래명세표 문장을 보완하고 공개 PDF를 35쪽으로 재생성했다. 기존 캡처를 유지했으며 공용 캡처 도구는 로컬 3201만 추가 허용했다.

## 회귀 검증

- 구현 전 `tests/integration/G-BIZ.test.ts` 6건 실패: 새 열 부재, 서버의 미지원 필드 거부, 가입 필드 부재를 확인했다. 새 E2E 3건은 관리자 대표자 필드와 360px 가입 업태·종목 입력 부재로 실패했다. 설명서 PDF 검증도 재생성 전 누락을 확인했다.
- 새 통합 6건: 실제 PostgreSQL 마이그레이션·nullable text·DB 길이 제약, 관리자 저장/빈값 삭제/길이 검증, 정산 담당자 조회·쓰기 금지, 선택 목록과 현장 담당자 HTTP 개인정보 제외, 공용/개별 가입 저장, 본인 수정·공유 및 CARRIER 차단·관리자 수정, 지정 가입 변조 거부·새 사업자 링크 저장, 거래명세표 셀 값·정산 XLSX/PDF 텍스트·확정 스냅샷 보존.
- 새 E2E 4건: 관리자 거래처 폼 저장 → 거래명세표 다운로드 실제 셀 확인, 360px `/join`·`/invite` 선택 필드/기본값/가로 넘침, 설명서 웹/PDF의 새 안내 확인.
- `npm run typecheck && npm run lint && npm run format:check && npm test` 통과: **90개 파일 / 540건**. 린트 경고 없음.
- 기존 F4-DETAIL 5건, F4-JOINBIZ 3건, JOIN-drivers 5건 및 새 G-BIZ·SEC2-identity·W6-settlement·MANUAL-captures 9건: **관련 E2E 총 22건 통과**.
- 일반 길이 및 최대 길이 사업자 정보의 명세 PDF 렌더링, 설명서 35쪽 전체 렌더링과 변경된 23·29·30쪽 확대 검증을 마쳤다. 새 npm 패키지는 추가하지 않았다. 오프라인 셸은 E2E의 predev에서 정상 빌드됐다.
- 모든 DB 실행은 `.env.local`, `PG_PORT=54401`, 명시적 로컬 DATABASE_URL만 사용했다. E2E는 같은 서버의 `vehicle_e2e`, 웹과 설명서 PDF 생성은 `PORT=3201`만 사용했다. E2E 전후 개발 DB 업무 건수는 동일하다. 운영 비밀 파일/DB는 접근하지 않았다.

## 공용 파일과 범위

- `src/server/db/schema.ts`, `src/server/authz.ts`: 새 열과 중첩 개인정보 제외 키만 추가.
- `src/components/manager/master-config.ts`, `master.tsx`: 사업자 필드 설정과 개별 maxLength 전달만 추가.
- `DriverInformationFields`, `DriverProfileEditor`, `JoinBusinessFields`와 관련 가입·프로필·기준정보 서비스는 공통 입력/검증 경로로 사용한다. 다른 작업자의 `users.tsx`, `drivers.tsx`, 기간 버튼 코드는 수정하지 않았다.
- `drizzle/meta/_journal.json`, `tests/integration/DEPLOY*.test.ts`, `docs/DESIGN.md`, `docs/API.md`, `docs/manual/capture/lib.mjs`와 설명서 본문·README·PDF를 갱신했다. 새 회귀 파일은 저장소 `tests/`에 있다.

## 선택한 해석과 남은 사항

- ‘본인 전용’은 활성 여부나 소속 기간과 관계없이 다른 기사 연결이 전혀 없는 사업자로 보수적으로 판단했다. 과거/미래 소속이 있는 거래처도 관리자가 수정한다. 기존 상호·사업자 변경과 차량 보호 규칙은 유지했다.
- 지정된 `scratchpad/allsites.xlsx`는 이 워크트리와 원 저장소 경로에서 찾을 수 없었다. 요청에 명시된 항목과 기존 F4-DETAIL 거래명세표 구조를 기준으로 완성했다. 고객 원본을 복사하거나 실명·번호를 테스트/캡처에 넣지 않았다.
- 남은 재현 결함 없음. 운영 배포 및 운영 DB의 0760 적용은 이 작업에서 실행하지 않았다.
