화물차 사용 내역과 청구 정산 앱 기획서
오픈소스 비교와 기사 담당자 공동 업무 설계
기준일 2026년 9월 29일  ·  버전 1.0
1 결정 요약
기사와 현장 담당자가 같은 차량 사용 내역을 확인하고, 승인된 비용만 월별 명세로 묶는 웹앱을 권장한다. 기사에게는 휴대전화용 입력 화면을, 담당자에게는 표와 필터 중심의 화면을 제공한다. 차량 사용대장과 증빙이 정산서의 원본이 되도록 만드는 것이 개발의 중심이다.
선택
권장 내용
첫 개발 방식
모바일 웹앱 PWA와 중앙 데이터베이스. 기사와 담당자가 역할별 화면으로 같은 원장을 사용한다.
우선 참고할 코드
Trippr의 사용내역과 청구서 구성, Warp Tools의 지급 원장과 미지급 관리. 공동 사용과 마감 기능은 별도로 설계한다.
큰 시스템을 도입할 조건
배차와 위치관제가 중요하면 Fleetbase, 회사 전반의 거래처·회계와 통합할 계획이면 ERPNext를 검토한다.
핵심 설계
차량 사용 계약 단위, 실제 운행 횟수, 과금 항목을 구분한다. 일대 차량의 반복 운행이 일대 중복 청구로 이어지지 않게 한다.
첫 버전 완료 기준
기사 입력부터 담당자 검수, 월말 확정, Excel/PDF 출력, 지급 확인까지 한 번의 마감을 끝낼 수 있어야 한다.

업무 범위는 외주 기사 또는 운송업체의 차량 사용료를 회사가 확인하고 지급하는 형태를 기본으로 둔다. 원청이나 다른 업체에 차량비를 다시 청구하는 경우에는 동일 운행에 별도의 청구금액과 청구상태를 연결한다. 사전 배차 없이 전화나 카카오톡으로 차량을 부른 후 등록하는 흐름도 지원한다.
아래 기능과 화면 구성은 이 업무를 위한 설계안이다. 오픈소스가 제공하는 기능은 출처와 함께 구분했다. 실제 운임, 계약 단위, 마감일과 문서 양식은 회사에서 사용하는 기준으로 설정한다.
2 오픈소스 후보 비교
저장소에 코드가 공개되어 있는지, 수정하여 사용할 수 있는 라이선스인지, 기사와 담당자가 함께 사용할 구조인지, 월별 정산 기능이 실제 구현되어 있는지를 각각 확인해야 한다. 다음 비교는 원 저장소·공식 문서와 일부 핵심 파일을 기준으로 한다.
후보
활용할 수 있는 부분
추가 개발과 판단
Trippr MIT
차량 사용 실적, 거래처별 단가, 추가비, Excel/CSV 가져오기, 실적을 선택해 PDF 청구서 생성. [S01–S03]
화면과 출력 아이디어 우선. 브라우저 저장 중심이므로 중앙 DB, 기사 계정, 승인, 마감과 지급 관리가 필요하다. [S04]
Warp Tools MIT
운행별 지급 원장, 정산기간, 실비·선지급·공제, 받을 돈과 줄 돈, 미수·미지급 화면. [S05–S08]
독립 도구 모음. 기사 포털·정산 PDF·다중 사용자 인증 등이 미완료로 명시되어 있어 부분 참고에 적합하다.
Fleetbase AGPL 계열
FleetOps의 배차·운송관리, Navigator 기사앱, 작업 증빙, Ledger 청구서·PDF·입금 기록. [S09–S12]
배차까지 필요한 확장형 기반. 국내 현장 검수·운송사별 월 합산·마감 규칙은 추가해야 한다.
ERPNext와 Frappe GPLv3와 MIT
거래처, 매출·매입 청구, 승인 Workflow, 기사·차량·다중 정차점을 포함한 Delivery Trip. [S15–S17]
업무 시스템 기반으로 적합. 기사 간편 입력과 차량비 전용 원장은 새로 만든다. 두 프로젝트의 라이선스를 구분한다.
Odoo Community와 OCA LGPLv3와 모듈별 조건
차량·운전자·노선·운행 모듈을 조합. OCA 18.0의 tms 모듈은 AGPL-3, 개발상태 Alpha로 명시. [S18a–S19]
이미 Odoo를 쓰는 경우 검토. 현재 브랜치에 없는 회계 기능이나 Enterprise 기능을 기본 제공으로 가정하지 않는다.
Traccar Apache 2.0
GPS 서버와 모바일 위치 전송, 경로·정차 이력. Client SDK를 별도 기사앱에 붙일 수 있다. [S20–S21]
위치 기능을 추가할 때 사용. 운임·담당자 검수·월말 청구 원장은 별도 개발한다.
InvoicePlane MIT
거래처, 청구서, 입금과 출력 양식. 이름과 로고 사용 조건은 코드와 별도로 확인한다. [S22–S23]
청구 화면과 양식 참고. 차량 사용 원장과 기사 입력 기능은 추가해야 한다.
Dolibarr GPLv3 이상
고객·공급업체와 청구·지급 업무의 기반. [S24]
기존 Dolibarr 사용 회사에 적합한 확장 후보. 신규 차량 앱에는 운송 업무 개발 비중이 크다.

2 1 우선 검토할 세 가지 접근
첫 선택은 경량 PWA를 새로 만들면서 MIT 코드의 필요한 부분을 검토해 가져오는 방식이다. Trippr는 사용내역과 청구서의 관계가 가깝고, Warp Tools는 지급·미지급 원장 구성이 가깝다. 두 앱을 통째로 합치기보다는 하나의 업무 데이터 구조를 먼저 정하고, 맞는 화면과 출력 코드를 옮기는 편이 명확하다.
두 번째는 ERPNext 위에 차량 사용 문서와 기사 입력 화면을 추가하는 방식이다. 회사 거래처와 구매·지급 관리까지 함께 다룰 때 이점이 있다. 세 번째는 Fleetbase를 기반으로 배차·기사 앱·관제를 운영하는 방식이다. 현 시점의 기록·정산 요구만으로는 이 전체 운영 구성을 선택할 이유가 충분하지 않다.
2 2 실제 파일에서 확인한 도입상의 차이
• Trippr의 청구 계산은 DutyEntry들의 일수를 합산한다. 이 항목을 그대로 “한 번 운반”으로 해석하면 같은 날 다섯 번 운반한 일대 차량에 다섯 일대가 계산될 수 있다. 앱이 의도한 항목 단위와 우리 회사 계약 단위를 맞춰야 한다. [S04]
• Warp Tools의 기사 정산 모듈은 기사 포털과 PDF를 Ideas 항목에 두고, 청구 모듈은 다중 사용자 인증을 미완료로 표시한다. 화면이 있다는 사실만으로 공동 업무에 바로 투입할 수 있는 상태는 아니다. [S06–S07]
• Fleetbase Ledger의 청구 초안 생성 시점은 주문 요금이 정해질 때다. 담당자가 사용실적과 추가비를 검수한 뒤 월말에 묶는 업무와 처리 시점이 다르므로 조정이 필요하다. [S12]
• OCA tms 18.0의 모듈 선언에는 개발상태 Alpha가 있다. 차량·기사·운행 모듈의 존재는 확인되지만, 이 정보로 월말 청구와 지급 기능의 완성도를 판단할 수는 없다. [S19]
2 3 라이선스와 후순위 후보
MIT·Apache 라이선스 후보는 원 저작권과 라이선스 등 요구 고지를 보존하면서 활용하는 방향으로 검토한다. GPL·AGPL도 상업 이용 자체가 금지되는 것은 아니지만, 배포 또는 수정본의 네트워크 제공 방식에 따른 해당 소스 제공 조건을 검토해야 한다. Fleetbase는 AGPL과 별도 상업 라이선스를 안내한다. 회사 전체 소스나 고객 데이터를 공개한다는 뜻으로 확대해서는 안 된다. [S02, S08, S13, S17, S20]
후순위 후보
확인한 이유
Invoice Ninja
Elastic License 2.0. 제3자에게 상당한 기능을 제공하는 호스팅·관리형 서비스에 제한이 있어 무조건 포크해 판매하는 기반으로 추천하지 않는다. [S30]
LoadPartner TMS
현재 Fair Core License 조건을 적용한다. 내부 활용과 경쟁 제품 제공 조건을 구분해야 하며, 현재 곧바로 Apache 라이선스 소프트웨어로 취급하면 안 된다. [S31]
CargoNext
README는 MIT, 실제 license.txt는 AGPL-3.0 이상으로 적혀 있다. 기능 아이디어를 참고하되 코드 채택 전 해당 버전의 권리를 정리해야 한다. [S32–S33]
LogisticsX
현재 공개 코드에 PolyForm Noncommercial 조건이 있고, 주요 클라이언트는 비공개 하위 저장소를 사용한다. 일반 회사의 무료 상업용 포크 후보에서 제외한다. [S34]

Fleetbase Navigator에는 위치 수집용 제3자 SDK 의존성도 있다. 확인한 4.x 계열 SDK는 Android 배포용 빌드에 별도 라이선스를 요구하므로, 앱 자체의 AGPL 표시와 별개로 의존성 조건을 확인하거나 위치 모듈 교체 범위를 잡아야 한다. [S14a–S14b]
활동 근거: Trippr 변경 이력은 2026년 8월 항목을, Fleetbase와 ERPNext 릴리스 목록은 2026년 9월 유지보수 활동을 보여준다. 활동이 있다는 사실과 운영 품질 검증은 별개다. [S03, S35–S36]
3 공동 업무 흐름
기사 또는 담당자가 사용기록을 만들고, 기사 제출과 현장 검수를 거쳐, 승인된 비용을 거래 상대방별 정산명세로 확정한다. 전화나 카카오톡으로 배차가 이루어져도 기록은 앱에 모을 수 있어야 한다. 국내 참고 서비스도 운송기록·증빙·정산을 연결하며, 현장 운반 전산은 주문 없는 직접 전표와 일대 계약을 다룬다. [S25–S27]
단계
행동과 결과
1 사용기록 생성
담당자가 사전 등록하거나 기사가 운행 후 등록한다. 실제 사용일과 작성일을 따로 저장한다.
2 실적 제출
차량·현장·운행과 작업내용을 확인하고 허용된 증빙을 첨부한다. 추가비가 있으면 사유와 함께 요청한다.
3 담당자 검수
작업 여부, 비용 귀속, 수량, 단가, 추가비와 증빙을 확인한다. 부족한 항목은 구체적인 보완 사유를 남긴다.
4 보완과 재제출
수정 전후 기록을 보존한다. 제출한 내용이 바뀌면 해당 버전을 다시 검수한다.
5 월별 명세 작성
기간과 운송사 등 거래 상대방을 정한다. 승인 완료·금액 확정·미정산 비용만 포함하고 보류 건을 따로 보여준다.
6 명세 확정
원본 항목, 단가, 수량, 합계, 거래 상대방과 승인 이력을 고정한다. 문서번호를 부여하고 Excel/PDF를 만든다.
7 지급 확인
지급 예정일과 실제 지급일·금액을 기록한다. 지급기록이 없는 명세는 미지급으로 남긴다.
8 후속 조정
전월 누락, 인정금액 변경과 이월은 원래 사용일을 유지한 채 조정 내역으로 처리한다.

• 휴대전화에서 큰 글씨와 누르기 쉬운 버튼을 사용하고, 날짜·전화번호·숫자 입력에 맞는 키보드를 제공한다.
• “휴대폰에 임시저장”과 “담당자에게 제출 완료”를 다르게 표시한다. 사진이 아직 업로드되지 않았으면 해당 상태를 따로 보여준다.
• 담당자의 보완 요청은 “하차 장소만 추가해 주세요”처럼 수정할 항목과 사유를 함께 보여준다.
• 운행 중 계속 조작할 필요가 없도록 출발 전 또는 정차 후 한 번에 기록하는 동선을 기본으로 한다.

5 3 정산서와 증빙 묶음
문서 상단에는 거래 상대방, 정산기간, 발행일, 문서번호와 담당자를 넣는다. 본문은 사용일·차량·현장·작업·단위·수량·단가·추가비·금액을 보여주고, 하단에는 공급가·세액·총액과 회사가 정한 확인란을 배치한다. 운행 순번을 누르면 해당 증빙과 승인 이력으로 연결되게 한다.
서로 다른 문서를 모두 청구서라고 부르지 않도록 차량 사용대장, 운송사 지급명세, 원청 청구명세, 거래명세, 외부 세금계산서의 목적을 화면에 표시한다. 앱의 PDF 출력과 외부 전자세금계산서 발행은 별도의 동작으로 관리한다.
6 전체 기능 목록
P0는 첫 공동 사용과 한 번의 월마감에 필요한 기능, P1은 반복 업무를 줄이는 확장, P2는 실제 수요가 확인된 뒤 추가할 기능이다. 기능마다 완료 기준을 제시했으며, 이는 새 앱의 요구사항이다. 후보 저장소에 모두 구현되어 있다는 의미는 아니다.
모든 P0 기능에는 서버 권한 검사, 계정 접근 회수, 전송 중복 방지, 금액 검증, 변경자와 시각 기록, 동시 수정 시 덮어쓰기 방지를 공통 기준으로 적용한다. 상세 버전 비교 화면과 충돌 해결 편의기능은 이후 추가할 수 있다. 기존 Excel 자료가 도입의 출발점이면 F066 가져오기도 첫 개발에 포함한다.

초대 기반 로그인
담당자가 초대한 기사와 직원만 계정에 연결하고, 휴대전화에서 반복 로그인 부담 없이 허용된 회사 업무에 접근한다. 완료 기준  초대받지 않은 계정은 접속할 수 없고, 만료되거나 사용한 초대 링크로 새 권한을 얻지 못한다.

F003 P0
현장별 자료 접근
기사는 본인 운행을, 담당자는 배정된 현장 자료를 조회하도록 제한하고, 첨부파일 다운로드와 명세서 출력에도 같은 권한을 적용한다. 완료 기준  다른 현장의 기록 번호나 파일 주소로 접근해도 내용이 노출되지 않고 내보내기 결과에서도 제외된다.
F004 P0
개인정보 최소 수집
운행 협업에 필요한 이름, 연락처, 차량과 거래관계만 우선 수집하고, 불필요한 신분증이나 민감정보 입력을 요구하지 않는다. 완료 기준  주민등록번호와 신분증 사본 없이 이용을 시작할 수 있고, 연락처는 업무상 필요한 사용자에게만 보인다.
F005 P1
임시 기사 이용 기간
일회성 외부 기사를 정해진 현장과 이용 기간에 연결하고, 업무 종료 후에도 회사의 과거 정산자료는 보존한다. 완료 기준  이용 기간이 끝난 기사는 새 기록을 만들 수 없으며, 담당자는 기존 운행과 정산내역을 계속 조회한다.
F006 P1
작업 확인과 금액 승인 분리
현장 작업을 확인하는 사람과 운임을 승인하는 사람이 다를 때 두 확인 절차와 책임자를 별도로 지정한다. 완료 기준  작업 확인만 완료한 기록은 금액 승인 대기로 남고, 금액 승인 권한이 없는 사용자는 정산을 확정하지 못한다.
F007 P2
여러 회사의 공간 분리
다른 회사에도 서비스를 제공할 경우 회사별 사용자, 거래처, 차량, 단가와 문서를 독립된 업무 공간으로 분리한다. 완료 기준  한 사람이 두 회사에 참여하더라도 선택한 회사의 자료만 보이며, 검색과 파일 접근도 회사 경계를 넘지 않는다.

F013 P2

회사가 보관하기로 정한 계약서나 자격 확인자료에 유효기간을 기록하고, 갱신 담당자에게 만료 예정만 안내한다. 완료 기준  자료 종류와 기한을 회사가 설정할 수 있으며, 만료 안내만으로 법적 자격이나 운행 가능 여부를 자동 판정하지 않는다.

제출과 수정의 버전을 보존하고, 검수자가 이전 값과 현재 값 및 작성자와 변경 사유를 한 화면에서 비교하도록 한다. 완료 기준  보완 전후의 장소와 금액 변경을 확인할 수 있으며, 이전 제출본이 최종 값으로 덮어써져 사라지지 않는다.
F045 P1
동시 수정 충돌 안내
기사와 담당자가 같은 기록을 동시에 수정하면 먼저 저장된 변경을 알려주고, 최신 내용을 확인한 뒤 다시 저장하도록 한다. 완료 기준  오래 열린 화면에서 저장해도 다른 사람이 수정한 값이 사라지지 않으며, 충돌한 항목을 안내받는다.

F048 P0
지급과 청구별 중복 사용 방지

F049 P0
정산 회차 확정과 취소
정산 회차를 확정하면 포함내역과 합계를 잠그고, 지급 전 오류는 사유를 남겨 회차를 취소한 후 새로 작성하도록 한다. 완료 기준  확정 회차를 직접 편집할 수 없으며, 지급 전 취소 시 원래 회차 이력과 취소 사유가 보존된다.
F050 P1
마감 후 증감 조정
이미 지급하거나 청구한 회차의 오류는 원본을 고치지 않고, 연결된 추가금액 또는 차감 항목으로 정정하여 근거를 남긴다. 완료 기준  지급된 원명세의 금액은 유지되고, 조정명세에서 원기록과 증감 사유 및 정정 후 잔액을 확인할 수 있다.
F051 P1
전월 누락과 보류 이월

F052 P2
여러 단계의 마감 승인
조직 규모상 필요하면 현장 담당자, 공무와 회계 담당자가 정해진 순서로 마감자료를 확인하고 승인 책임을 나눈다. 완료 기준  지정된 선행 승인이 없으면 최종 확정이 막히고, 반려하면 어느 단계에서 다시 확인해야 하는지 표시된다.

F055 P1
부분지급과 잔액
한 명세를 여러 번 나누어 지급할 수 있도록 지급 건별 일자와 금액을 기록하고, 누적 지급액과 남은 금액을 계산한다. 완료 기준  10만 원씩 두 번 지급하면 누적액은 20만 원으로 표시되고, 남은 금액이 있는 명세는 완납으로 바뀌지 않는다.
F056 P1
선지급과 차감 항목

F057 P2
외부 지급 시스템 연동

원청 재청구 관리

F059 P1

같은 운행의 지급단가와 원청 청구단가를 따로 보존하고 상대방별로 공개할 금액을 제한하며, 재청구가 필요하면 우선 개발한다. 완료 기준  기사 지급액을 변경해도 원청 청구액이 자동으로 바뀌지 않고, 기사 화면에는 원청용 단가가 노출되지 않는다.

F061 P1
입금과 미수금 관리
재청구 명세의 입금일과 수금액을 기록하여 미수금을 확인하고, 재청구가 핵심 업무이면 단일 완납 기록부터 첫 버전에 넣는다. 완료 기준  원청 입금을 기록해도 기사 지급 상태는 바뀌지 않으며, 입금되지 않은 청구명세의 잔액을 조회할 수 있다.
F062 P2
여러 청구처의 분할 청구

F063 P2
현장 원가와 예산 비교
차량비 예산을 쓰는 현장은 승인 비용과 실제 지급액을 구분해 예산 대비 사용을 보고, 재청구 수입과 비교할 수 있게 한다. 완료 기준  미확정 예상비와 승인 원가가 섞이지 않으며, 같은 비용을 운행 합계와 배분 합계에서 이중 계산하지 않는다.

F076 P1
보관 기간과 접근 이력
회사가 정한 보관 기간에 따라 자료를 정리하고, 민감한 조회와 다운로드 및 권한 변경의 이력을 확인하도록 한다. 완료 기준  보관 중인 정산 근거가 임의 삭제되지 않으며, 정리 대상과 처리 결과 및 중요 접근 이력을 확인할 수 있다.
F077 P1
ERP와 회계 자료 전달
확정된 비용과 거래처 및 현장 코드를 회사 ERP가 요구하는 형식으로 전달하고, 전송한 회차와 반영 결과를 기록한다. 완료 기준  이미 전달한 회차를 구분할 수 있고, 같은 회차를 다시 전송해도 외부 장부에 중복 반영되지 않도록 식별한다.
F078 P2
전자세금계산서 연동 상태
정산내역을 세금계산서 서비스와 연결할 필요가 있으면 발행요청, 발행결과와 외부 문서번호를 보관하고 업무 상태만 연계한다. 완료 기준  앱의 명세 확정과 외부 발행 완료를 구분하며, 연동 오류만으로 세금계산서가 발행된 것으로 표시하지 않는다.
F079 P2
필요한 운행의 위치 공유
현장 도착 확인이 실제로 필요할 때만 운행 시간 동안 위치 공유를 제공하고, 이용자가 공유 중인지 확인하고 종료할 수 있게 한다. 완료 기준  선택한 운행이 끝나면 위치 수집이 종료되며, 위치 기능을 쓰지 않는 기록도 사용대장과 정산을 작성할 수 있다.
F080 P2
운송 정보망 연동
외부 차량 수배가 필요해지면 허용된 정보망 연동으로 요청과 배차결과를 가져오고, 내부 운행 및 정산 원장과 연결한다. 완료 기준  외부 오더가 재전송되어도 내부 요청은 하나로 연결되며, 배차 완료만으로 운행 완료나 지급 완료가 처리되지 않는다.

7 개발 순서와 검증 기준
처음부터 모든 기능을 구현하지 않고 실제 현장 한 곳과 소수 기사로 기록·검수·마감 전체 흐름을 검증한다. 아래 기간은 일정 약속이 아니라 작업 묶음이다. 실제 개발 일정은 기존 코드의 재사용 정도, 사용자가 쓰는 양식, 계약 규칙과 연동 범위를 확인한 뒤 산정한다.

7 1 꼭 통과해야 하는 업무 시나리오
검증 항목
기대 결과
일대 반복 운행
일대 300,000원 차량에 운행 상세 5건을 등록해도 기본 지급액은 300,000원이다.
같은 경로 반복
같은 날짜·차량·경로로 실제 두 번 운행하면 두 원본을 보존하고, 중복 경고만 제공한다.
전송 중복
동일 제출을 두 번 보내거나 연결 복구 후 재시도해도 원본과 비용은 한 번만 생성된다.
이중 마감
담당자 두 명이 같은 비용을 동시에 서로 다른 명세에 넣으려 하면 한 쪽만 확정된다.
지급과 재청구
같은 운행의 지급 비용과 원청 청구 비용은 각각 정산할 수 있으며 서로의 중복 제약을 침범하지 않는다.
과거 단가 보존
단가표를 다음 달 값으로 변경해도 이미 승인·확정된 과거 명세와 PDF의 금액이 변하지 않는다.
승인 후 변경
승인된 운임 또는 증빙을 바꾸면 변경된 버전은 다시 검수되고, 과거 승인 이력이 남는다.
월 경계
9월 사용분을 10월에 정산해도 실제 사용일은 유지되고, 어느 달에 청구했는지 조회된다.
사진 업로드 실패
사용기록 저장에 성공해도 필수 사진 전송이 실패하면 제출 완료 또는 승인 가능 상태로 오인되지 않는다.
권한 경계
기사 A가 기사 B의 번호나 첨부 주소를 직접 요청해도 B의 실적·단가·증빙을 읽을 수 없다.
확정 후 취소
확정명세는 임의 삭제되지 않으며, 취소·조정이 원본 문서와 연결되어 추적된다.
합계와 복구
명세 화면·Excel·PDF 금액이 일치하고 백업에서 복원한 기록과 첨부의 연결이 유지된다.

8 기술 구성과 운영
8 1 PWA를 첫 선택으로 권하는 이유
PWA는 지원하는 브라우저에서 홈 화면 아이콘을 추가하고 앱처럼 열 수 있는 웹앱이다. 담당자는 PC에서, 기사는 Android 휴대전화에서 같은 서비스를 이용할 수 있다. 사용내역 입력·사진 첨부·검수·출력이 중심인 이 업무에 적합하다. 설치 방식과 일부 기능 지원은 브라우저별로 다르다. [S28]
통신이 끊겼을 때는 작성 중 자료와 첨부를 기기에 임시저장하고, 앱을 다시 열면 서버로 재전송한다. Background Sync만 믿고 브라우저가 종료되어도 항상 전송된다고 표시해서는 안 된다. 기본 동작은 미전송 표시, 재접속 시 재시도, 수동 재전송으로 구성한다. [S29]
휴대전화 화면이 꺼진 상태에서도 장시간 위치를 수집해야 한다면 Android 또는 크로스플랫폼 앱과 네이티브 위치 기능을 별도 개발한다. 그때 Traccar 서버나 Client SDK를 연결하는 선택지가 있다. 위치를 정산의 유일한 증거로 삼지 않고 해당 사용기록의 보조 자료로 연결한다. [S20–S21]

새 프로젝트가 TypeScript 웹 기반이라면 Trippr와 Warp의 화면 코드를 비교하기 쉽다. ERPNext를 선택하면 Frappe 문서와 권한 체계에 맞추고, Fleetbase를 선택하면 그 모듈·API 구조를 사용한다. 서로 다른 세 가지 백엔드를 한꺼번에 결합하는 구성을 기본값으로 삼지 않는다.

처음에는 한 업무 서버와 DB로 시작하고 실제 동시 사용량으로 크기를 정한다.

업로드 크기 제한·압축·보존기간을 정하고 원본이 필요한 증빙은 정책에 따라 보존한다.

앱 내 알림을 기본으로 하고 문자·알림톡은 실제 필요한 이벤트와 승인된 연동에 한정한다.
지도와 위치
주소록과 즐겨찾기로 시작하고 지도·지오코딩·상시 위치 비용은 필요 시 추가한다.
전자문서·ERP
전자세금계산서와 ERP API는 계약·호출비·연동 지원 범위를 별도로 확인한다.
AI
원장 계산은 정해진 규칙으로 처리한다. 사진 읽기·음성 입력을 추가할 때만 호출하고 사람이 확인한다.
유지보수
백업·장애 대응·보안 업데이트·현장 양식 수정도 운영 범위와 담당자를 정한다.

용량 예시: 월 1,000건에 사진 2장씩, 압축 후 한 장 1MB라면 사진은 월 약 2GB가 쌓인다. 백업·복제·다운로드 트래픽은 별도다. 이는 서비스 견적이 아닌 용량 산정 예시다.
